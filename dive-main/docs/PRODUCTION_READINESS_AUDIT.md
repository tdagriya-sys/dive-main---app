# Production Readiness Audit — 2026-08-05

A full sweep of the backend (Express/TS/Mongo) and frontend (React CRA) for functionality gaps, security, scalability (caching/queueing/rate-limiting/indexing), and deployment readiness. Findings are ordered P0→P3 by how much they'd actually hurt in production, not by category — a P0 blocks shipping at all; a P3 is real but can wait.

This complements two existing docs rather than duplicating them: `DIVE_SCORE_MODEL.md` §13 (deliberate scoring-model scope decisions) and `PROTOTYPE_LIMITATIONS.md` (deliberate prototype-stage simplifications). Everything below is either a genuine bug/gap, a silent failure mode, or a place code has drifted from what those docs claim — not a re-litigation of decisions already made on purpose.

---

## P0 — Blocks shipping to production at all

1. **No deploy configuration exists anywhere in the repo.** No `Dockerfile`, `docker-compose.yml`, `Procfile`, or platform config (`render.yaml`, `vercel.json`, etc.) for either frontend or backend. The only deploy-adjacent file (`.emergent/emergent.yml`) is metadata for the current prototyping platform, not a portable deploy artifact. Deploying to any real host is entirely unaddressed today. *(backend + frontend)*

2. **OTP can leak straight into the signup API response in production.** `backend/src/services/otpService.ts` + `backend/src/controllers/authController.ts` — if `EMAIL_API_KEY` (OTP delivery moved from SMS to email — see `docs/GETTING_API_KEYS.md` §1) is left as its `.env.example` placeholder, `devOtp` is returned in the JSON response, not just logged. `checkProductionSafety()` (`backend/src/index.ts:8-19`) blocks a dev JWT secret or in-memory Mongo from starting under `NODE_ENV=production`, but does **not** check `emailApiKeyIsPlaceholder` — a real deploy that forgets to set a real email key ships with a full OTP-gate bypass, silently. (Note: a *real delivery failure* with a real key configured is already handled correctly and does NOT leak — that path was fixed to hard-fail in production instead of falling back to exposing the code; this finding is specifically about the placeholder-key case, which still bypasses silently.)

3. ~~**No React error boundary anywhere in the frontend.**~~ **Fixed 2026-08-07.** `frontend/src/components/ErrorBoundary.jsx` (new) — two boundaries now mounted: an outer catch-all around the whole app (`index.js`) as a last-resort full-page fallback, and an inner one around `<DiveShell/>` inside the phone frame (`App.js`) so a bug in one screen shows a contained "this screen hit a snag, try again" state without blanking the landing page's header/marketing copy around it. Both offer a retry (re-render without reload) and the outer one also offers a full reload. Verified live by deliberately throwing in both `Onboarding` (inner) and `Landing` (outer) — each boundary caught its error correctly, logged it via `console.error`, and the outer boundary's landing-page chrome stayed intact while the inner one was broken.

4. ~~**The production JWT-secret safety check is a weak substring match, not a real strength check.**~~ **Fixed 2026-08-08.** `checkProductionSafety()` (`backend/src/index.ts`) now checks `env.jwtAccessSecretIsWeak`/`env.jwtRefreshSecretIsWeak` instead of the old `.includes("dev-")` check. Those flags come from a new `isWeakJwtSecret()` helper in `env.ts` that combines the existing `isPlaceholder()` regex (catches the literal `.env.example` placeholder, `REPLACE_WITH_A_LONG_RANDOM_SECRET`) with a minimum-length floor of 32 characters (catches any short/guessable secret, including the old `"dev-...-change-me"` fallback string itself, which `isPlaceholder()`'s `CHANGE_ME` regex never actually matched since the fallback uses a hyphen, "change-me", not an underscore). Verified directly: the `.env.example` placeholder, the old dev fallback, and a short arbitrary string all correctly flag as weak, while a real `openssl rand -base64 48`-style secret passes.

5. ~~**No health/readiness endpoint, no graceful shutdown.**~~ **Fixed 2026-08-07.** Added `GET /api/health` (`backend/src/app.ts`) — checks real Mongo connectivity via `mongoose.connection.readyState`, returns 503 if disconnected rather than just confirming the process is alive. Mounted under `/api` specifically so it's reachable through the Nginx reverse-proxy in `docs/SERVER_DEPLOYMENT_GUIDE.md` (which only forwards `/api/*` to this backend). Added `SIGTERM`/`SIGINT` handlers in `backend/src/index.ts` — stop accepting new connections (`server.close()`), let in-flight ones finish, cleanly `disconnectDb()`, then exit, with a 15s force-exit safety timer in case a stuck keep-alive connection would otherwise hang the shutdown forever. Verified live: the health endpoint correctly returns `{"status":"ok","db":"connected",...}` at 200 while up. Graceful shutdown was verified by emitting `SIGINT` *in-process* (`process.emit`) rather than via a real OS signal — Windows (this dev machine) doesn't reliably deliver cross-process signals to Node the way the actual Linux/PM2 deploy target does (confirmed empirically: `process.kill(pid, "SIGINT")` from a separate process just force-terminated the target with no handler invoked, twice, consistent with Node's documented Windows signal-emulation limits), so the in-process emit is what actually exercises the registered listener's logic — it correctly logged `received SIGINT, shutting down gracefully...` → closed the server → disconnected Mongo → `shutdown complete`.

## P1 — Breaks the moment there's real traffic or more than one instance

6. **Rate limiting silently stops working with 2+ backend instances.** `backend/src/middleware/rateLimit.ts` and the global `/api` limiter (`app.ts:38-47`) both use `express-rate-limit`'s default in-memory store — no shared store (Redis) configured. Each process tracks its own counters, so effective limits multiply by instance count with zero error or warning.

7. **The daily instrument-refresh cron has no distributed lock.** `backend/src/jobs/instrumentRefresh.cron.ts` runs unconditionally in every process (`index.ts:37`). With 2+ instances, the 6am refresh fires N times concurrently, each hammering AMFI/NSE/CoinGecko independently — wasteful and risks tripping CoinGecko's rate limit for all instances at once.

8. ~~**No rate limiting at all on the endpoints that cost real money per call.**~~ **Fixed 2026-08-08.** Added `aiIngestLimiter` (`backend/src/middleware/rateLimit.ts`) — 10 requests per 15 minutes — mounted on both `POST /api/uploads` and `POST /api/botscan/analyze` (`upload.routes.ts`, `botscan.routes.ts`), placed after `requireAuth` and before the multer upload middleware so an over-limit request is rejected before its body is even parsed. The two routes deliberately share one limiter instance/bucket rather than getting one each, so a user can't double their effective ceiling by splitting abuse traffic across both endpoints. Keyed by the authenticated `userId` (not IP) — closes the loop an IP-based limit would leave open (single account, rotating IPs) and also sidesteps `express-rate-limit`'s default IP-format validation, which otherwise throws a noisy `ValidationError` behind the Nginx reverse-proxy setup unless `trust proxy` is explicitly configured (a separate, still-open item — see the `trust proxy` note surfaced during live debugging). Verified in isolation with a throwaway Express harness (real limiter instance, fake `req.userId`, no DB/Anthropic calls involved): 10 requests succeed, the 11th and 12th both return `429`, and a second user with a different `userId` gets an independent bucket rather than sharing the first user's count.

9. ~~**IP-based rate limiting has no `trust proxy` configuration.**~~ **Fixed 2026-08-09 — confirmed as a real, live production incident, not just a theoretical gap.** This is exactly what it warned about: a handful of admin-testing login calls on the live site exhausted the shared bucket, and every subsequent login/signup attempt — from every device, including ones that had never made a single request — started getting rejected, since they were all landing in that one collapsed bucket. Fixed with `app.set("trust proxy", "loopback")` in `app.ts`, added before any middleware reads `req.ip`. `"loopback"` (not `true`) matches this deployment's actual topology exactly — Nginx runs on the same machine as the backend, proxying to `localhost:8000` — so `X-Forwarded-For` is only trusted when the connection genuinely arrives via 127.0.0.1/::1, not from anywhere (which `true` would allow, letting a client spoof their own IP if port 8000 were ever reachable directly — it isn't, per the UFW rules in the deploy guide, but `"loopback"` doesn't rely on that alone). Immediate mitigation for the live incident: `pm2 restart divve-backend` (rate-limit counters are in-memory, wiped by a restart). Verified the actual fix with a real test simulating Nginx's exact position (requests over loopback, each carrying a different `X-Forwarded-For`): exhausting the login limiter for one simulated device leaves a second, different device completely unaffected — confirming independent buckets instead of one shared one. Full backend suite (65 tests, 10 suites) passes.

10. ~~**Refresh tokens are never rotated and have no server-side revocation.**~~ **Fixed 2026-08-08.** Added a `RefreshToken` collection (`backend/src/models/RefreshToken.ts`) keyed by a random `jti` embedded in the JWT itself (never the raw token — `signRefreshToken` now takes a `jti` and returns `{ token, expiresAt }`, `utils/jwt.ts`). Every refresh token now has a matching DB record created through one shared `issueRefreshToken()` helper (`authController.ts`), used by `signupVerify`, `login`, and `refresh` alike, so it can't drift out of sync. `refresh()` now rotates on every call: it atomically claims-and-revokes the presented token (`findOneAndUpdate({ jti, revokedAt: null }, { revokedAt: new Date() })`, so two concurrent refresh calls with the same cookie can't both succeed) and issues a fresh one. Presenting an *already-revoked* token (rotated away, or logged out) is treated as reuse/theft — it revokes every other still-live token for that user too, not just the one presented, so a stolen token can't keep working via a delayed replay. `logout()` now revokes the presented token's DB record instead of only clearing the cookie. Old records are auto-purged via a Mongo TTL index on `expiresAt` once they naturally expire, kept around until then so a replay after rotation can still be recognized. Verified end-to-end against the real app + an in-memory Mongo (login issues one live record; first refresh rotates it and succeeds; replaying the old cookie is rejected with `REFRESH_TOKEN_REUSED` and kills the legitimately-rotated token too; logout followed by a refresh attempt is rejected) — all 10 checks passed. Frontend needed no changes: both call sites (`lib/api.js`'s 401 interceptor, `DiveContext.js`'s session-restore) already treat any failed `/auth/refresh` generically as "session gone, log out."

11. **Bot Scan / file upload block the HTTP request on a synchronous, untimed Claude API call.** `backend/src/controllers/botScanController.ts:27`, `uploadController.ts:52-57` — no queue, no explicit timeout on the Anthropic call. A large scan holds an Express connection open for the full extraction latency; under concurrent load this ties up workers and risks load-balancer timeouts (typical 30-60s defaults) before Claude even replies. **Update 2026-08-25:** `aiExtractionService.ts` now tries OpenAI (GPT-5.6 Terra) first and falls back to Claude Sonnet 5 only if that call fails — same still-open queueing/timeout gap described above, but worst-case latency on the fallback path is now roughly double (up to ~120s: one full OpenAI attempt, then one full Claude attempt) rather than a single provider's ~60s ceiling. Not yet addressed by a queue/async job architecture; the existing 60s-timeout-plus-cancel-button mitigation from item #32 still applies to whichever call is currently in flight.

12. **Account Aggregator "real mode" is structurally incomplete, not just gated on missing credentials.** `backend/src/controllers/aaController.ts` + `finvuService.ts` — the only path that moves a consent from `PENDING`→`ACTIVE` is `approveMockConsent`, hard-gated to `consentHandle.startsWith("mock-")`. There is **no webhook/callback route anywhere** for Finvu's real server-to-server consent-approval flow, `FINVU_CERT_PATH` is read from env but never actually used to set up mTLS, and the default `FINVU_BASE_URL` is a non-resolvable placeholder domain. Configuring real Finvu credentials today would not produce a working integration — it would hang at PENDING forever. This is a meaningfully bigger gap than `PROTOTYPE_LIMITATIONS.md` §4 currently implies ("sandbox until credentials are configured") — worth updating that doc once this is either built out or the framing is corrected.

13. ~~**Context-level data loaders silently swallow errors and present them as empty/unchanged state.**~~ **Fixed 2026-08-08.** All three sub-issues addressed: (1) `loadHoldings` (`DiveContext.js`) no longer clears `holdings` to `[]` on failure — it now sets a new `holdingsError` flag and returns the last-known-good list (tracked via a `holdingsRef`), so a transient failure can no longer make a real portfolio look empty. `Home.jsx` now branches on this: empty + `holdingsError` renders a distinct "Couldn't load your portfolio" screen with a retry button (`HoldingsLoadError`), separate from the genuine empty-portfolio state (`EmptyHome`). (2) `savePrefs` now rolls back to the previous value and returns `true`/`false` instead of silently swallowing a failed `PATCH`; `Preferences.jsx` wraps every call site through a `handleSavePrefs` helper that shows a save-error banner (`prefs-save-error`) when it returns `false`. (3) `lib/api.js` now exposes `setSessionExpiredHandler`, called from the response interceptor's catch block when a refresh attempt ultimately fails on a 401 from any endpoint (not just the initial page-load check); `DiveContext.js` registers a handler that clears the session and returns to `splash`, so a mid-session expiry now actually forces re-login instead of leaving the app stuck showing stale data with every subsequent request failing silently. Verified live in the browser end-to-end against the real dev server: signed up a real test user, added a real holding, confirmed Home renders normally; killed the backend mid-session and confirmed (a) toggling a preference shows the rollback + error banner (chip visibly reverted from "Aggressive" back to "Balanced") and (b) Home kept showing the real dashboard/score throughout the outage rather than reverting to the empty-portfolio state. The session-expiry handler itself was verified by code review plus the already-proven-correct server-side revocation behind it (10/10 checks from the #10 fix above) — triggering the exact mid-session-expiry race live would need an artificially expired access token, which wasn't worth the added scope here.
