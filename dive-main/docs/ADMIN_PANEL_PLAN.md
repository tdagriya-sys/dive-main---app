## 1. Goals

1. One instance, one login. Credentials decide the surface: staff → admin shell (`/admin`), everyone else → the current app (`/`). Every admin endpoint independently enforces permission; the frontend split is UX only.
2. Every factor in the **Dive Score model**, **Context (Layer D) model**, **Look-through / connectedness model**, and **Suggestion layer** is editable from the admin panel — with versioning, validation, a simulation sandbox, diff, rollback, and a full audit trail.
3. Manage and monitor **users** and **activity**; monitor **revenue**; create and manage **subscription plans**; enforce **plan entitlements** across the product.
4. **Super admin / admin** roles plus **custom employee roles** with granular, resource-scoped permissions; employee invite flow; mandatory 2FA for all staff.
5. **Support tickets** (in-app, with outbound email replies), **notifications** (in-app + email, category-wise, segmented, scheduled), and **detailed audit logs** of every action.
6. Plus the full set of "commonly missed" admin capabilities listed in §11.

## 2. Architecture decisions (locked)

| Topic | Decision |
|---|---|
| Instance | Same backend, same repo, same deploy. Admin API under `/api/admin/*`. |
| Surface routing | Introduce `react-router-dom` (already a dependency, v7) at the app root. `/` → existing screen-state app (unchanged), `/admin/*` → new `<AdminApp>`, **lazy-loaded** so the user bundle doesn't grow. Nginx already serves the SPA catch-all. |
| Authz | Access token stays `{ sub }` only. Role + permissions resolved per-request from DB (no token reissue on role change — same rationale as today's `requireAdmin`). New `requireStaff` + `requirePermission("x")` middleware. `ADMIN_EMAILS` kept only as the first-superadmin bootstrap, then deprecated. |
| Scoring config | New **versioned MongoDB collections**. Scoring services load the **active config** (cached, invalidated on publish), falling back to `DEFAULTS` = today's exact hardcoded values. Behaviour is byte-identical until an admin edits something. |
| Queue / cache | **Redis** + **BullMQ** for jobs (notification sends, config simulations, exports, email retries) and `rate-limit-redis` for a shared limiter store (fixes audit P1 #6). Redis also caches entitlement/usage lookups. |
| Dev database | Points at the **live MongoDB cluster**. ⚠️ Use a **separate database name** for dev/staging (`DB_NAME=dive_staging`) — see the setup guide. Backend Jest suite stays isolated via `mongodb-memory-server`. |
| Staff 2FA | **Mandatory TOTP for every staff role** (superadmin, admin, employee). Enrolled during invite acceptance; enforced before any admin action. |
| Support | In-app tickets + outbound email replies via Resend. **No inbound email parsing** in scope. |
| Analytics | **In-house `ActivityEvent` store** (no third-party). |
| Push | **In-app + email now.** Push deferred (revisit with the Capacitor/Android effort). |
| Impersonation | **Read-only.** Time-boxed, banner-marked, every request tagged with `impersonatingUserId` in the audit log. |
| Observability | Add `pino` structured logging + request-id middleware + Sentry in Phase 0 (prerequisite for trustworthy audit logs and system health). |

## 3. Subscription product spec (locked)

Two plans. All existing users become **Freemium** on launch (migration + in-app announcement).

### 3.1 Freemium (free)

| Capability | Limit | Enforcement |
|---|---|---|
| Bot Scan AI extraction | **1 / week AND 3 / month** (whichever is reached first blocks) | `enforceUsage("bot_scan")` on `POST /api/botscan/analyze` |
| Doc Upload AI extraction | **1 / week AND 3 / month** (separate counter from bot scan) | `enforceUsage("doc_upload")` on `POST /api/uploads` |
| Portfolio edits | **2 / week AND 5 / month** (whichever first). Counts holding create + update + delete. | `enforceUsage("portfolio_edit")` in `holdingsController` create/update/delete |
| Daily portfolio revaluation | **Off** — every holding's value stays exactly as entered (market-priced and FD/PF alike) | `holdingValuationService.runDailyValuationRefresh()` filters to Premium users only |
| Auto-updated Dive Score | **Off** — score recomputes only when the user manually edits holdings/profile | Natural consequence of frozen values + existing cache invalidation |
| Early access to new features | No | `FeatureFlag.enabledForPlans` excludes `freemium` |
| Support | Standard ticket priority | Ticket default priority |
| Resilience report PDF (₹99 one-off) | Available, unchanged | Existing `Payment` / `SCORE_REPORT_PDF` flow |

### 3.2 Premium — ₹119/month, or ₹1099/year (12 months, ~23% off)

**15-day free trial** on first subscribe (`SubscriptionPlan.trialDays`, editable from admin). During the trial the user has full Premium entitlements; first charge fires at trial end; cancel-during-trial = no charge, revert to Freemium.

| Capability | Limit |
|---|---|
| Bot Scan AI extraction | **3 / week AND 10 / month** |
| Doc Upload AI extraction | **3 / week AND 10 / month** |
| Portfolio edits | **Unlimited** |
| Daily portfolio revaluation | **On** (current `valuationRefresh.cron.ts` behaviour: `quantity × latest price`, FD/PF interest accrual) |
| Auto-updated Dive Score | **On** — score reflects daily value drift |
| Early access to new features | **Yes** — feature flags gated to `premium` |
| Support | **Priority** (ticket auto-priority `high`, shorter SLA) **+ on-call** (user can request a callback from the ticket screen; staff see the request with the user's mobile) |
| Resilience report PDF | **Not included** — remains a separate ₹99 one-off for both tiers. |

### 3.3 Pricing internals

| Plan key | Interval | Amount (paise) | Razorpay plan |
|---|---|---|---|
| `premium_monthly` | `month`, interval 1 | `11900` | created via admin "Publish to Razorpay" |
| `premium_annual` | `year`, interval 1 | `109900` | created via admin "Publish to Razorpay" |

- Prices are **GST-inclusive** (consumer-facing). Invoice shows base + 18% GST (see §12 / setup guide for GSTIN details needed).
- Razorpay subscription created with a large `total_count` (e.g. 120 monthly cycles) = "until cancelled".
- `cancelAtPeriodEnd` supported; access continues to `currentPeriodEnd`, then downgrades to Freemium.

### 3.4 Usage-metering design (rolling windows)

- **`UsageEvent`** collection: `{ userId, key, ts }` — one row per metered action, TTL index ~35 days. Enforcement = `countDocuments({ userId, key, ts: { $gte: now - windowMs } })` for each of the 7-day and 30-day windows.
- **Windows are rolling**: last 7 × 24 h and last 30 × 24 h (not calendar-aligned). "Resets" messaging shows when the oldest counted event ages out.
- `enforceUsage(key)` middleware: resolve the user's plan → limits; count both windows; if either is at/over its limit → `403 PLAN_LIMIT_REACHED` with `{ key, window, limit, resetsAt, upgradeUrl }`; else `next()` and record the `UsageEvent` **only after** the underlying action succeeds (a failed AI call doesn't burn quota).
- **Portfolio edits are coalesced into _edit sessions_**: the first holding mutation (create / update / delete) or AA sync **opens an edit session** — a Redis key `edit-session:{userId}` with a sliding TTL (`EDIT_SESSION_WINDOW_MIN`, default 20 min, admin-editable). While a session is open, further mutations only refresh its TTL and are **not** counted. So "add 3 stocks then finish" = 1 edit, one AA sync = 1 edit, edits days apart = separate. An explicit client "done" signal (`POST /api/holdings/edit-session/close`) also ends the session early. The `UsageEvent` + limit check happen only at session **open**.
- The existing `aiIngestLimiter` (10 / 15 min, abuse ceiling) stays **on top** of plan limits.
- Redis caches the plan + limits lookup (short TTL) to keep the hot path cheap.
- All metered actions also emit an `ActivityEvent` for analytics (`UsageEvent` is for enforcement, `ActivityEvent` is for reporting).

### 3.5 Entitlement service

`backend/src/services/entitlementService.ts`:
- `getPlan(userId)` → active `Subscription` → `SubscriptionPlan`, else the built-in `FREEMIUM` plan.
- `getEntitlements(userId)` → merged entitlement object (limits + feature booleans).
- `assertEntitlement(userId, key)` for boolean gates.
- Used by: usage middleware, `holdingValuationService`, feature-flag resolution, `GET /api/score/breakdown` (no detail gating today, but hook is there), the frontend (via `GET /api/me/entitlements`).

## 4. Data model — new collections

Grouped by area. All timestamps `Asia/Kolkata`-aware where user-facing.

### 4.1 Identity & access
- **`User`** (extend): `staffRole?: "superadmin"|"admin"|"employee"|null`; `roleId?: ObjectId→Role`; `status: "active"|"suspended"|"deleted"` (default `active`); `staffMeta?: { invitedBy, invitedAt, acceptedAt, lastAdminLoginAt, totpSecret, totpEnabled, totpEnrolledAt }`. Also apply `passwordHash: { select: false }` (audit #29) while here.
- **`Role`**: `key`, `label`, `description`, `permissions: string[]`, `isSystem: boolean` (superadmin/admin seeded, undeletable), `createdBy`, timestamps.
- **`StaffInvite`**: `email`, `staffRole` | `roleId`, `tokenHash`, `expiresAt`, `status: "pending"|"accepted"|"revoked"|"expired"`, `invitedBy`.
- Permission registry — **code, not a collection**: `backend/src/auth/permissions.ts`. See §6.

### 4.2 Scoring / context / suggestion configuration (all versioned; shared lifecycle draft → validate → simulate → publish → rollback)
- **`ScoringConfig`**: `version`, `status: "draft"|"active"|"archived"`, `parentVersion`, `publishedBy`, `publishedAt`, `changeNote`, and the payload:
  - `compositeWeights` — the 10 keys of `DIVE_SCORE_V2_WEIGHTS` (must sum to 1.0 ± 0.001).
  - `subScoreRanges` — `{ volatility:{worstAt,bestAt}, drawdown:{...}, var:{...}, beta:{...}, correlation:{...}, diversificationRatio:{...} }` (each fed to `scoreFromRange`).
  - `concentrationSubWeights` — `{ apparent:0.50, real:0.15, name:0.20, withinClass:0.15 }`.
  - `liquidityTiers` — per `AssetClass`, 0–100.
  - `stockCountBreakpoints` — `[[count,score],...]`, monotonic in count.
  - `withinClassAdjustments` — `{ cryptoCap:70, equitySectorSpreadTarget:5, fdLadderBlendEnabled:true }`.
  - `singleClassCorrelationScores` — `{ whenExpectedClassesLE1:50, otherwise:20 }`.
  - `drawdownUnrecoveredPenalty` — `15`.
  - `syntheticParams` — per `AssetClass` `{ drift, vol, beta }` (score doc §4.2).
  - `scoreBands` — `{ labels:[...], colors:[...] }` (`scoreLabel`/`scoreColor` thresholds).
  - `varMonthlyScaling` — `sqrt(21)` factor (exposed for completeness).
- **`ContextConfig`**: `corpusTiers[]` `{ id, label, maxAmount, expectedClassCount, reasoning }`; `personaBrackets[]` `{ id, label, minAge, maxAge, priorityClasses[], deprioritizedClasses[], volatilityWorstAt, drawdownWorstAt, reasoning }` (age ranges must be contiguous, non-overlapping, cover 18→∞); `defaultClassOrder[]` (permutation of the 12 classes).
- **`LookthroughConfig`**: `tierStrengths` `{ sameSectorSameClass:0.3, exactIssuer:1.0, sectoralMfMatchingEquity:0.15 }`; `keywordSectorAffinity` (rows: `keyword → { GOLD?:0.25, SILVER?:0.15, ... }`); `industryAssetClassAffinity` (rows: `nseIndustry → { REIT?:0.3, ... }`); `mfSegmentToNseIndustry` (rows); `mutualFundTopHoldings` (rows: `fundKey → [{ issuer, weightPct }]`); `mutualFundSegmentKeywords` (rows). These replace `backend/src/seed/sectorAffinity.ts`, `mutualFundTopHoldings.ts`, `mutualFundSegments.ts` as the runtime source (seed files become the initial-import fixtures).
- **`SuggestionConfig`**: `idealRanges` `{ Conservative:{Equity:[lo,hi],...}, Balanced:{...}, Aggressive:{...} }`; `coreCategories[]`; `returnTier` (category → low/medium/high); `returnBias` (Modest/Moderate/High → −1/0/1); `diversificationCap` (Low/Medium/High → 2/3/∞); `fastPathBlend` `{ apparent:0.65, real:0.15, name:0.20 }` (`diveEngine.js`'s `diveScore()`).
- **`ConfigSimulation`**: `{ configType, draftVersion, sampleSize, filters, distributionBefore, distributionAfter, deltaHistogram, biggestMovers:[{segmentLabel, before, after, delta}], runBy, runAt, status }`. Movers are described by **segment**, never by user identity.
- **`ConfigChangeLog`** (or reuse `AuditLog` with `resourceType:"scoring_config"`): human-readable published-change feed, powers the auto-generated doc appendix.

### 4.3 Users, activity, revenue
- **`ActivityEvent`**: `{ userId?, sessionId?, type, props, ip, userAgent, ts }`. Types: `signup`, `login`, `logout`, `session_restore`, `holding_added`, `holding_edited`, `holding_deleted`, `aa_sync`, `bot_scan`, `doc_upload`, `score_viewed`, `breakdown_viewed`, `report_purchased`, `report_downloaded`, `subscription_started`, `subscription_renewed`, `subscription_cancelled`, `plan_limit_reached`, `ticket_created`, `notification_opened`, `feature_used`. Write is thin, fire-and-forget, batched (queue-flushed every few seconds or N events). Monthly rollup collection **`ActivityDailyRollup`** for long-horizon aggregates; raw events TTL after ~180 days.
- **`SubscriptionPlan`**: `{ key, name, description, pricePaise, interval:"month"|"year"|"one_time", trialDays, entitlements:JSON, razorpayPlanId?, isActive, visibility:"public"|"hidden"|"legacy", displayOrder }`. Seeded with `freemium`, `premium_monthly`, `premium_annual`.
- **`Subscription`**: `{ userId, planId, status:"trialing"|"active"|"past_due"|"cancelled"|"expired", currentPeriodStart, currentPeriodEnd, razorpaySubscriptionId?, razorpayCustomerId?, cancelAtPeriodEnd:boolean, startedAt, endedAt?, lastPaymentId? }`. Index `(userId, status)`.
- **`Payment`** (extend): `purpose` gains `SUBSCRIPTION_INITIAL`, `SUBSCRIPTION_RENEWAL`; add `subscriptionId?`, `invoiceId?`, `refundedAmountPaise?`, `refundIds?:string[]`, `failureReason?`.
- **`Invoice`**: `{ number, userId, subscriptionId?, paymentId, lineItems:[{desc, sacCode, qty, unitPaise}], subtotalPaise, gstRatePct:18, gstAmountPaise, totalPaise, placeOfSupply, sellerGstin, buyerName, pdfKey, issuedAt }`. (Phase 6b.)
- **`Coupon`** (optional, Phase 6b): `{ code, type:"percent"|"flat", value, appliesToPlanKeys[], maxRedemptions, redeemedCount, expiresAt, isActive }`.
- **`WebhookEvent`**: `{ provider:"razorpay"|"resend", eventType, payloadHash, payload, signatureValid, processedOk, error?, receivedAt, processedAt? }`. Idempotency guard + debugging (would have saved days on audit #34/#35).
- **`UsageEvent`**: see §3.4 — `{ userId, key, ts }`, TTL ~35 days.
- **`SubscriptionPlan.trialDays`** default `15` for the premium plans, editable from admin. Trial applies on a user's **first ever** Premium subscription only (tracked via `Subscription` history / a `hasUsedTrial` flag on `User`).

### 4.4 Support
- **`Ticket`**: `{ refNo, subject, categoryKey, priority:"low"|"normal"|"high"|"urgent", status:"open"|"pending"|"resolved"|"closed", requesterUserId?, requesterEmail, requesterName, assigneeId?, tags[], source:"contact_form"|"in_app"|"seed", slaDueAt?, firstRespondedAt?, resolvedAt?, closedAt?, csatScore?, csatComment?, callbackRequested?:{ requestedAt, mobile, preferredWindow, done } }`.
- **`TicketMessage`**: `{ ticketId, authorType:"requester"|"staff"|"system", authorId?, body, attachments:[{key,name,size,mime}], isInternalNote:boolean, emailMessageId?, createdAt }`.
- **`TicketCategory`**: `{ key, label, defaultAssigneeId?, defaultPriority, slaHours, isActive }`.
- **`CannedResponse`**: `{ title, body, categoryKey?, createdBy }`.
- Migration: existing `ContactSubmission` rows → one `Ticket` + one `TicketMessage` each (`source:"contact_form"`).

### 4.5 Notifications
- **`NotificationCategory`**: `{ key, label, description, defaultChannels:["in_app"|"email"], userOptOutAllowed:boolean, isSystem }`. Seeded: `account`, `score`, `subscription`, `product`, `support`, `marketing`.
- **`NotificationTemplate`**: `{ key, name, categoryKey, subject, bodyMarkdown ({{var}} placeholders), channels[], isActive }`.
- **`NotificationCampaign`**: `{ name, templateKey?, inlineContent?, categoryKey, audience:"all"|"segment"|"user_ids", segmentQuery?:JSON, userIds?[], scheduleAt?, status:"draft"|"scheduled"|"sending"|"sent"|"cancelled"|"failed", stats:{ targeted, sent, delivered, opened, failed }, createdBy, sentAt? }`.
- **`UserNotification`**: `{ userId, campaignId?, categoryKey, title, body, link?, channel, deliveredAt, readAt?, emailStatus?:"queued"|"sent"|"bounced"|"failed" }`. Powers the header bell (currently a client-only stub in `AppHeader.jsx`).
- **`UserNotificationPref`**: `{ userId, categoryKey, channel, enabled }`. Absent row = category default.
- Segment builder targets: plan, subscription status, signup date range, has-holdings, holdings count, last-active window, Dive Score band, city (if known), specific user list.

### 4.6 Audit & ops
- **`AuditLog`** (append-only; no update/delete route ever): `{ actorId, actorRole, impersonatingUserId?, action, resourceType, resourceId?, diff:{ before?, after? } | jsonPatch, ip, userAgent, requestId, ts, meta, prevHash?, hash? }`. Optional hash-chain for tamper-evidence. Long TTL or scheduled archival export to cold storage.
- **`FeatureFlag`**: `{ key, description, enabled, rolloutPct:0-100, enabledForUserIds[], enabledForPlanKeys[], updatedBy, updatedAt }`.
- **`AdminSetting`** (key/value singleton store): announcement banner `{ text, level, enabled, dismissible }`, maintenance mode `{ enabled, message }`, support settings, default SLA, feature-preview list, etc.
- **`SystemJobRun`**: `{ job, startedAt, finishedAt?, ok?, error?, stats, host }`. Wraps `instrumentRefresh.cron.ts`, `valuationRefresh.cron.ts`, notification sends, simulations, exports.
- **`DataRequest`** (DPDP): `{ userId, type:"export"|"delete", status, requestedAt, fulfilledAt?, fileKey?, handledBy? }`.

## 5. Backend work

### 5.1 Auth & RBAC
- `backend/src/auth/permissions.ts` — permission constants + `ROLE_DEFAULTS` (superadmin = all; admin = all except `roles.manage`/`employees.manage`/`scoring_config.publish` unless granted; employee = whatever their `Role.permissions` say).
- `middleware/auth.ts` — add `requireStaff`, `requirePermission(perm)`, `requireStepUp` (password or fresh TOTP within N minutes). Keep `requireAuth`. `ADMIN_EMAILS` → bootstrap only.
- TOTP: `speakeasy` (or `otpauth`) + QR at enrolment. Enforced in `requireStaff` (reject with `TOTP_ENROLMENT_REQUIRED` / `TOTP_REQUIRED` until a valid code is presented for the session).
- Staff session hardening: `STAFF_ACCESS_TTL` (short, e.g. 10m) applied when `staffRole` set; optional `ADMIN_IP_ALLOWLIST`.
- Staff invite: `POST /api/admin/employees/invite` → Resend email → `POST /api/auth/staff/accept-invite` (set password, enrol TOTP, accept).
- First superadmin: `backend/src/scripts/createSuperadmin.ts` (`tsx`), promotes an existing user by email and forces TOTP enrolment on next login. See setup guide.
- Impersonation: `POST /api/admin/users/:id/impersonate` (perm `users.impersonate`, step-up) → short-lived read-only token carrying `{ sub: targetId, imp: staffId, readOnly: true }`. All write endpoints reject `readOnly` tokens. Banner in UI. Auto-expires (e.g. 30m). Every request audited.

### 5.2 Config-driven scoring engine
- `backend/src/services/config/` — `getActiveScoringConfig()`, `getActiveContextConfig()`, `getActiveLookthroughConfig()`, `getActiveSuggestionConfig()`. In-memory cache + explicit `invalidate*` on publish. Each returns a fully-populated object; missing document → `DEFAULTS` constant (= current hardcoded values, extracted verbatim).
- Refactor to **inject config** (pure functions):
  - `diveScoreService.ts::computeDiveScoreBreakdownUncached` takes `{ scoringConfig, contextConfig, lookthroughConfig }`.
  - `contextEngine.ts::resolveContext` takes `contextConfig`.
  - `lookthroughService.ts::computeLookthroughOverlap` takes `lookthroughConfig`.
  - `stats.ts::scoreFromRange` unchanged; only its arguments become config-sourced.
- `GET /api/score/config` — **public, cacheable** — returns the non-sensitive frontend subset: `suggestionConfig.idealRanges`, `coreCategories`, `returnTier`, `returnBias`, `diversificationCap`, `fastPathBlend`, plus context labels/reasoning strings for messaging. `frontend/src/lib/diveEngine.js` and `contextMessaging.js` fetch + cache this (via `DiveContext` on load), keeping current hardcoded values as offline fallback.
- **Validation** (Zod, on publish): weights sum to 1.0; every range pair `worstAt ≠ bestAt`; tiers in `[0,100]`; breakpoints monotonic; persona age ranges contiguous & total; every `AssetClass` covered in liquidity + synthetic params + default order.
- **Versioning / rollback**: publish = active → archived, draft → active, `version++`, write `AuditLog` diff + `changeNote`. `POST /api/admin/scoring-config/:version/rollback` re-publishes an archived version as a new version.
- **Simulation sandbox**: `POST /api/admin/{configType}/simulate` → BullMQ job → run the draft config against a sample of real portfolios (holdings shape only, no PII), return distribution shift + delta histogram + biggest movers by segment. Renders as a chart + table in the editor **before** the publish button is enabled.
- **Doc reconciliation**: `GET /api/admin/scoring-config/export-doc` renders the active values as a markdown appendix; `DIVE_SCORE_MODEL.md` §Maintenance updated to say methodology lives in the doc, live values live in the config + this export, and every publish requires a `changeNote` appended to the visible changelog.
